# IVF（倒排索引）

倒排索引是现代搜索引擎的核心数据结构。它的核心思想是" **用内容找文档** "，而不是我们通常理解的"正排索引"（通过文档找内容）。

## 索引构建过程

构建倒排索引是一个将原始文档集合转换为可快速查询的数据结构的过程。主要分为以下几个步骤：

**1\. 文档收集与解析**

**输入**一组文本文档（网页、PDF、Word等）**，**需要从各种格式的文档中提取出纯文本内容。

**2\. 词法分析 / 分词**

将连续的文本流切分成独立的、有意义的词项（Term）。

例如，"倒排索引很好用" 会被切分成 \["倒排索引"， "很"， "好用"\]。

**3\. 文本预处理**

目的是归一化词项，减少索引体积，提高查询准确性。常用技术包括：

**转小写、去除停用词（**如"的"、"是"、"a"、"the"等**）、词干提取（**例如 "running", "runner", "runs" 都被还原为 "run"**）**。

**4\. 构建索引**

遍历所有文档，为每个预处理后的词项建立到一个**倒排记录表**的映射，本质上是一个 **字典（或哈希表）**。

## 索引查询过程

当用户输入一个查询（例如"科技 公司"）时，搜索引擎会：

- **对查询进行同样的分词和预处理** ： 得到词项 \["科技", "公司"\]。
- **从倒排索引中查找**：分别取出"科技"和"公司"对应的倒排记录表。
- "科技" -> \[文档1\]"公司" -> \[文档1, 文档2\]
- **求交集**： 对于"与"查询（默认），需要找到 **同时包含** 所有查询词的文档。即求两个列表的交集：\[文档1\] ∩ \[文档1, 文档2\] = \[文档1\]。
- **相关性排序** ： 根据词频、文档长度、词项在文档中的重要性等多种因素（如TF-IDF、BM25等算法）对结果文档进行打分和排序，将最相关的结果排在前面。
- **返回结果** ： 将排序后的文档列表返回给用户。

## 场景案例

假设我们有一个小型图书数据库，包含5本书：

**查询需求** ：查找所有包含"分布式"和"系统"两个关键词的书籍。

**正排索引**

- **查询步骤**：需要扫描5个文档的全部内容**，**找到文档1("分布式系统设计与实现")
- **时间复杂度**：O(N×M)，N=文档数(5)，M=查询词数(2)
- **缺点** ：文档数量很大时（如百万级），性能极差。

**倒排索引**

**查询步骤 ：**

- 查找"分布式" → 得到列表 \[1, 3\]
- 查找"系统" → 得到列表 \[1, 5\]
- 求交集：{1,3} ∩ {1,5} = {1}
- 返回结果：\[1\]

**时间复杂度** ：O(L₁ + L₂)，其中L₁、L₂是倒排列表长度

**倒排索引将海量文档的搜索问题转化为了少数几个列表的集合运算问题。**

## 优势

- **极高的查询效率**： 对于关键词查询，其时间复杂度接近 O(1)（哈希查找）或 O(log n)（字典树查找），再加上对有序倒排列表求交集的线性时间。这使得它能够应对海量数据和瞬时并发的搜索请求。
- **易于扩展**： 可以通过 **分片** 技术将巨大的索引分布到多台机器上，实现水平扩展。
- **支持复杂查询**： 可以高效地处理布尔查询（AND, OR, NOT）。
- **支持排名**： 倒排记录表中存储的附加信息（如TF）是进行相关性排序的基础。

## 劣势

- **构建成本高** ： 为海量文档集构建完整的倒排索引需要大量的计算和存储资源，耗时较长。
- **更新操作昂贵** ：
  - **添加文档**： 相对容易，只需对新文档分词并更新索引。
  - **删除文档**： 通常采用标记删除的方式，在合并时真正删除。
  - **更新文档**： 等价于先删除旧文档，再添加新文档。代价高昂。
- **解决方案**： 搜索引擎通常采用" **主索引 + 增量索引** "的策略，定期合并以平衡实时性和效率。
- **存储开销大** ： 虽然会对倒排列表进行压缩，但索引文件的大小通常远大于原始文本数据。
